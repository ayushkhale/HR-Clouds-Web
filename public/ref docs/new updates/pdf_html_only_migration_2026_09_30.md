# PDF Generation — HTML-only Renderer Migration & Bulk Generation Block

**Date:** 2026-09-30
**Module:** PDF Generation (Payroll + Documents planes)
**Audience:** Frontend engineers
**Plan:** `public/md_updates/2026-09-30_html_only_renderer_migration_plan.md`

---

Every PDF the backend produces is now rendered from HTML by the external renderer service. The
in-process PDFKit renderer has been removed. No request shape changed. What changed is **which
errors a PDF download can return**, **three bulk endpoints are temporarily switched off**, and
**one payroll setting is now ignored**.

## 1. Bulk PDF generation is switched off — `503 PDF_BULK_GENERATION_DISABLED`

Until ops turns bulk generation back on (env `PDF_BULK_GENERATION_ENABLED=true`), these calls are
refused **before anything is read or written**:

| # | Endpoint | When it is refused |
|:--:|---|---|
| 174 | `GET /api/v1/payroll/hr/runs/:id/payslips/download` (run payslip ZIP) | Always |
| 143 | `POST /api/v1/documents/hr/letters/bulk` (bulk letter issue) | Always |
| 219 | `POST /api/v1/payroll/hr/jobs/payslip-render/run` | Only when the body carries `run_id` |

- **Status:** `503`
- **Error code:** `PDF_BULK_GENERATION_DISABLED`
- **Message:** `Bulk PDF generation is temporarily disabled. Download documents individually.`

**What the frontend should do:**
- Hide or disable the "Download all payslips (ZIP)" and "Bulk issue letters" actions, or show the
  message above when the call returns this code.
- Do **not** retry automatically. This is a platform switch and does not clear on its own.
- Point users to the per-employee downloads, which still work (see §2).

**Not affected:** `#219` **without** `run_id` still drains the queue normally. `#147` (letter
re-enqueue) and polling of existing letter batches and render status keep working, so jobs
accepted before the switch still finish.

Also, publishing a payroll run no longer pre-renders payslips in the background while the switch is
off. Each payslip is rendered the first time someone downloads it.

## 2. Single-document PDF downloads can now return renderer errors

These endpoints used to render in-process and did not fail for renderer reasons. They now call the
renderer service:

| Document | Endpoints |
|---|---|
| Payslip | `GET /api/v1/payroll/hr/employees/:userId/payslips/:runId/pdf`, `GET /api/v1/payroll/manager/employees/:userId/payslips/:runId/pdf`, `GET /api/v1/payroll/me/payslips/:runId/pdf` |
| Annual statement | `GET /api/v1/payroll/hr/employees/:userId/annual-statement/pdf`, `GET /api/v1/payroll/me/annual-statement/pdf` |
| Form 16 Part B | `GET /api/v1/payroll/hr/employees/:userId/tax/form16/:financialYear/pdf`, `GET /api/v1/payroll/me/tax/form16/:financialYear/pdf` |
| Reports (`format=pdf`) | `GET /api/v1/payroll/{hr,manager}/reports/{payroll-register,department-distribution,deduction-summary,components}?format=pdf` |

New error responses to handle (JSON error body, not a PDF):

| Status | Error code | Meaning | Suggested UI |
|:--:|---|---|---|
| `409` | `PDF_RENDER_IN_PROGRESS` | The same document is being generated by another request | Retry once after ~2 s |
| `500` | `PDF_RENDER_FAILED` | The renderer rejected the document | "Could not generate the PDF"; offer a manual retry |
| `500` | `PDF_PAYLOAD_TOO_LARGE` | The document data exceeded the renderer's input cap | Suggest CSV or a narrower filter; do not retry |
| `502` | `PDF_RENDERER_UNAVAILABLE` | The renderer failed or returned a bad document | "Could not generate the PDF, please try again shortly" |
| `502` | `STORAGE_UNAVAILABLE` | The generated PDF could not be stored | Same as above |
| `503` | `PDF_RENDERER_NOT_CONFIGURED` | The renderer is not configured on this environment | "PDF generation is unavailable"; do not retry |
| `504` | `PDF_RENDER_TIMEOUT` | The renderer timed out | Offer a manual retry |

Success responses are unchanged: `200`, `Content-Type: application/pdf`, same filename header.
Reports keep their existing `422` row cap (2000 rows) for `format=pdf`.

**Retry safety:** a manual retry after a `502`/`504` is safe and does not create duplicates. A
failed attempt no longer blocks later attempts for the same document.

## 3. Visual changes (no contract change)

- **Held payslips** now use the same HTML design as released payslips. They are still rendered on
  demand and never cached.
- **Payroll reports** (`format=pdf`) use a new landscape HTML layout. The column-fitting rule is
  unchanged: columns that don't fit are dropped and a note points to the CSV export.
- **Payslips, annual statements and Form 16** for any org that was still on the old engine now
  get the HTML layout. The figures and fields are the same.

## 4. `pdf_render_engine` setting is deprecated and ignored

`PUT /api/v1/payroll/hr/settings`:
- `pdf_render_engine` still **validates** (`'pdfkit' | 'html'`) and is still **returned**, so
  existing forms don't break. It has **no effect**.
- Saving `'html'` no longer returns `409 PDF_RENDERER_NOT_CONFIGURED`.
- **Remove the engine toggle from the settings UI.** The column will be dropped in a later
  release. Stop sending the field before then.

`payslip_prerender_on_publish` still saves normally, but has no effect while bulk generation is
off (see §1).

## 5. Response fields that are now constant

| Endpoint | Field | Now |
|---|---|---|
| `GET /api/v1/payroll/hr/runs/:runId/payslips/render-status` | `engine` | Always `'html'` |
| `POST /api/v1/payroll/hr/jobs/payslip-render/run` (#219) | `engine` | Always `'html'` |
| `POST /api/v1/payroll/hr/jobs/payslip-render/run` (#219) | `engine_html_orgs` | Counts every org drained (previously only orgs that had opted in) |

If the UI branches on `engine === 'pdfkit'`, that branch is now dead code and can be removed.

## 6. Removed behaviour

- `#174` no longer has an in-process "legacy" ZIP path. When bulk is re-enabled, it will only use
  the cached HTML path (`200` streamed ZIP, or `202` with a `batch_id` above the
  `pdf_bulk_inline_miss_threshold`).
