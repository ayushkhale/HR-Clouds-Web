## 1. Goal & Boundary

**Goal.** Everything that is paid or recovered *on top of* the salary structure. Phase 2 answers *"what does this person's structure earn them this month, after LOP?"*; Phase 3 answers *"what else is added to or taken out of this month's pay, who authorised it, and can it happen twice?"*

Three capabilities, one shared spine:

1. **`payroll_adjustments`** — the single variable-pay line table. Every one-off earning or deduction lands here, whether it was typed by HR, proposed by a manager, uploaded in a CSV batch, or generated by a bonus rule.
2. **`bonus_rules`** — a declarative rule that *materialises* adjustments for an eligible population, with a persist-nothing impact preview.
3. **`employee_loans` + `loan_installments`** — principal, interest, a generated EMI schedule, outstanding balance, foreclosure, and automatic single-charge pull into the run.

Plus the two arithmetic behaviours the parent assigned to this phase: **negative net pay** (EC-14) and **EMI insufficiency** (EC-15).

### 1.1 Explicitly in scope

* 4 tables, 4 models, 4 repositories, 4 services, 4 new **pure** utility modules, **38 endpoints (#57–#94)**.
* Extension of `computePayrollItem` with Steps 6b and 8b–8d and the **deduction waterfall** (§5.5) — still a pure function, still no `db` import.
* A second cohort-batched, read-only aggregator for variable-pay inputs (**D-17**), keeping query count O(cohorts).
* Commit-at-approval / reverse-at-cancel for adjustments and installments (**D-18**) — the anti-double-pay guarantee.
* Hierarchy-scoped maker–checker (D-13 Tier B) on all three entities, reusing the Phase-1 `employee_salary_structure.service` shape verbatim.
* 2 new org settings (registry **#45–#46**) and unit suites for every pure module.
* Two pre-existing defects repaired because Phase 3 cannot work around them: the settings-update schema (§11 item 15) and unreserved engine component codes (§2 item 18).

**Build order is §12.** Read it before writing the first line — steps 5 → 7 → 8 are the chain that can corrupt money, and the ordering exists to keep them under passing tests.

> **Honesty guard, carried forward.** Phase 3 adds gross-side and deduction-side money but still applies **no statutory withholding**. A bonus is paid at 100% of its face value with no TDS. Every item keeps `statutory_status: 'not_applied'`, and the run's `engine_version` moves **2 → 3** so a figure can always be attributed to the engine that produced it. A Phase-3 `net_pay` must never be presented to an employee as final take-home.

Each is a fact verified in the live Phase-1/Phase-2 code, and each one silently breaks Phase 3 if missed.

3. **`computePayrollItem` already returns a `warnings` array and the run service discards it** ([payroll_run.service.js:404](src/modules/payroll/services/payroll_run.service.js#L404)). Phase 3 must persist it — `LOAN_EMI_SKIPPED` and `NEGATIVE_NET_CLAMPED` are operationally meaningless if they evaporate. This is an existing gap, not new work.
4. **`ENGINE_OWNED_COLUMNS`** in [payroll_run_item.repository.js:22](src/modules/payroll/repositories/payroll_run_item.repository.js#L22) is the UPSERT allow-list. **Every new engine-written column on `payroll_run_items` must be added to it**, or recalculation will silently leave the first calculation's value in place.
5. **`payrollRunRepo.create` hard-codes `engine_version: 2`** ([payroll_run.service.js:228](src/modules/payroll/services/payroll_run.service.js#L228)). 6. **`buildSettingsSnapshot` is an explicit allow-list** ([payroll_run.service.js:74](src/modules/payroll/services/payroll_run.service.js#L74)). A new engine knob that is not added there is **not** in the run's frozen snapshot and the engine will read `undefined`. `negative_net_handling` must be added.
7. **`payroll_run_items` is not paranoid and is hard-deleted by `pruneAbsent`.** Any FK pointing at it must be `ON DELETE SET NULL`, never `RESTRICT`.
8. **The advisory-lock idiom is `pg_advisory_xact_lock(hashtext(:key))` and it releases at COMMIT.** Multi-transaction flows are guarded by *status*, not by the lock (Phase 2 §7.2). Phase 3 adds no multi-transaction flow — every Phase-3 write is a single short transaction.
9. **`toPaise` rejects negatives by default** (`422 NEGATIVE_MONEY`, [money.utils.js:67](src/modules/payroll/utils/money.utils.js#L67)). Every Phase-3 amount is stored and transported **positive**; direction is carried by `component_type` / `adjustment_type`, never by a sign. The only negative line in the system remains `source: 'rounding'`.
10. **`percentOfPaise(basePaise, pct)` already exists** and is exact to 4 decimal places of percentage. Bonus percentages and flat-interest maths use it; do not hand-roll percentage arithmetic.
11. **Express 5: `req.query` is getter-only.** Every list endpoint validates query params **inside the controller** via `validateOrThrow`.
12. **`getAccessibleUserIds` returning `null` is not authority** — `decideAuthority` ([payroll_access.utils.js:51](src/modules/payroll/utils/payroll_access.utils.js#L51)) is the chokepoint and additionally requires `role === 'hr'` for global scope (D-14). Every Phase-3 manager path calls it; none re-implements it.
13. **`decideAuthority` already returns `canPropose` / `canApproveFor` / `canApproveReason`** and handles `payroll_require_separate_checker` and `manager_direct_compensation_authority`. Phase 3 **consumes** it unchanged — no new authority logic, no new role list.
14. **No upload infrastructure exists.** No `multer`, no `busboy`, no `req.files`, no CSV library anywhere in `src/`. `express.json({ limit: '10mb' })` is the only body parser. See **D-19**.
15. **`requires_recalculation` + `409 RUN_STALE` already exist** and already block approval ([payroll_run.service.js:899](src/modules/payroll/services/payroll_run.service.js#L899)). Phase 3 reuses that exact mechanism for late-approved variable pay (**D-18**) — no new staleness concept.
16. **`lock.service.checkLock` is the period gate** and is called by every attendance mutation. Payroll's own writers do **not** call it; Phase 3 uses the *run status* for the same purpose (**EC-31**, §6.4).
17. **`updateSettingsSchema` is missing every Phase-2 setting** — it stops at `manager_direct_compensation_authority` ([payroll_hr.validator.js:151-162](src/modules/payroll/validators/payroll_hr.validator.js#L151-L162)) and never gained `lop_basis`, `net_pay_rounding`, `in_progress_treatment` or the four overtime keys. `validateOrThrow` runs `{ allowUnknown: false, stripUnknown: true }`, so the key is **silently stripped**, and the failure mode depends on what else is in the body (verified by executing the schema):

   | Request body | Result |
   |---|---|
   | `{ "lop_basis": "fixed_30" }` | `400 VALIDATION_ERROR: "value" must have at least 1 key` — confusing, but at least loud |
   | `{ "lop_basis": "fixed_30", "currency": "INR" }` | **`200 OK`** — `lop_basis` is dropped, `currency` is saved, and HR is told the update succeeded |

   The second row is the real defect: a **silent, successful-looking write that discards the setting**. **Registry entries #41–#44 are unreachable through the API today, and attempting to set them can report success.** See §11 item 15 — Phase 3 fixes this in the same edit that adds #45–#46, because otherwise its own settings inherit the same dead end.
18. **Engine-generated component codes are not reserved.** `salary_components` has a unique partial index on `(org_id, code)` and an `is_system` immutability guard, but nothing stops HR creating a catalog component coded `OVERTIME` or `ROUNDING_ADJUSTMENT` — the two codes Phase 2's engine already synthesises. Phase 3 adds two more (`NET_PAY_SHORTFALL_CARRIED`, `CARRY_FORWARD_RECOVERY`) and must reserve **all four** (§11 item 3).

## 4. Database Schema — Migration `00040-create-payroll-variable-pay.js`

Same shape as `00038`: one `queryInterface.sequelize.transaction()`, tables in FK dependency order, partial unique indexes `WHERE deleted_at IS NULL`, CHECK constraints via raw `ALTER`, and `down()` reversing and dropping every generated enum type with `CASCADE`.

**Conventions.** UUID PK `defaultValue: Sequelize.UUIDV4` · `org_id` UUID NOT NULL FK → `organizations` (`CASCADE`/`CASCADE`) · `created_at`/`updated_at` NOT NULL · `underscored: true`.

**Paranoid policy (extends D-16).** All four new tables are **paranoid** — every one is a user-authored financial artefact whose deletion must leave a tombstone. `loan_installments` is paranoid too: it is *generated*, but it carries a money amount that was or was not charged, and an auditor must be able to see a schedule that was replaced.

**Create order:** `bonus_rules` → `payroll_adjustments` (FK → `bonus_rules`) → `employee_loans` → `loan_installments`, then the `addColumn`s on `payroll_settings` and `payroll_run_items`.

## 5. Core Logic

### 5.1 `loan_schedule.utils.js` (pure)

```
buildSchedule({ principal, annualRatePercent, tenureMonths, method, startPeriodMonth })
  → { emi_amount, total_interest, total_payable, installments: [{ n, due_period_month, principal, interest, total }] }
```

All arithmetic in **integer paise** via `money.utils`; no floats except the single `Math.pow` in the reducing-balance EMI formula, whose result is immediately converted to paise and never re-used.

* **`flat`** — `total_interest = principal × rate × tenure / 1200` (via `percentOfPaise`); `total_payable = principal + total_interest`; nominal `emi = total_payable / tenure`. Each installment splits `principal/tenure` and `interest/tenure`.
* **`reducing_balance`** — monthly rate `i = rate / 1200`; `emi = P·i·(1+i)^n / ((1+i)^n − 1)`, rounded half-up to paise once. Then amortise: `interest_k = round(outstanding_k × i)`, `principal_k = emi − interest_k`, `outstanding_{k+1} = outstanding_k − principal_k`.
* **`rate = 0`** — both methods collapse to `principal / tenure`, zero interest. No division-by-zero branch needed beyond guarding `(1+i)^n − 1 == 0`.
* **Balancing invariant (mandatory).** The **final** installment absorbs every rounding residue: `principal_n = outstanding_n` and `interest_n = total_payable − Σ(all other totals) − principal_n`. The builder asserts `Σ principal == principal_amount` and `Σ total == total_payable` **exactly, in paise**, and throws `SCHEDULE_RECONCILIATION_FAILED` otherwise. This is the loan-side equivalent of EC-17.
* `due_period_month` for installment *k* is `startPeriodMonth + (k−1)` months, computed by string arithmetic on `'YYYY-MM'` — no `Date` object (Phase 2 §2 item 9).

### 5.2 `bonus_rule_evaluator.utils.js` (pure)

```
evaluateRule({ rule, candidates }) → { awards: [{ user_id, amount, basis, basis_amount }], skipped: [{ user_id, reason }] }
```

`candidates` is `[{ user_id, department_id, employment_type, joining_date, monthly_gross, basic_monthly }]` — assembled by the service, never read here.

* **Eligibility** is filtered in this order: `eligibility_source` set membership → `employment_types` → `min_tenure_months` (computed against the rule's `period_month` end, month arithmetic on strings) → has a resolvable basis.
* **Amount:** `flat` → `value`; `percent_of_gross` → `percentOfPaise(monthly_gross, value)`; `percent_of_basic` → `percentOfPaise(basic_monthly, value)`. Then capped at `max_amount_per_employee` when set.
* **`performance_rating`** evaluates to `{ awards: [], skipped: [all, reason: 'ELIGIBILITY_SOURCE_UNAVAILABLE'] }`. The service turns that into a `422` on *apply* and shows it plainly on *preview*. **No hard dependency on a Performance module** (D-9).
* An employee with **no approved structure overlapping the rule's period** is `skipped` with `NO_SALARY_STRUCTURE`, never awarded ₹0.

> **The percentage basis is the salary structure, not the payslip (D-21).** `percent_of_gross` and `percent_of_basic` resolve against the employee's **approved salary structure effective at the rule's `period_month` end** — `monthly_gross` and the `is_basic` component's `monthly_amount`. They do **not** use the run's computed, LOP-reduced gross. Two reasons: a rule is evaluated and approved *before* the run exists, so a run-based basis would make the preview a lie; and a bonus that shrinks because someone took unpaid leave is a policy decision no one made. State this on the preview response as `basis: 'structure_monthly_gross' | 'structure_basic'`.

### 5.3 `variable_pay_selector.utils.js` (pure)

```
selectDueInstallments({ installments, periodMonth }) → [{ ...installment }]   // at most one per loan_id
selectApplicableAdjustments({ adjustments, periodMonth, runId }) → [...]
```

* **One installment per loan per run, always.** The selector takes, per `loan_id`, the **earliest `scheduled` installment whose `due_period_month <= periodMonth`**. Never two — a month in which two installments are due (because one was skipped, EC-15) charges one and lets the schedule slide.
* An installment already `deducted`, or already stamped with a **different** `run_id`, is never selected.
* An adjustment is applicable when `status === 'approved'` **and** (`applied_run_id` is null **or** equals this run). The second clause is what makes recalculating an already-approved run a no-op rather than a data-loss event.

### 5.4 `csv_parser.utils.js` (pure) — **D-19**

Hand-written RFC-4180 subset parser. `parseCsv(text, { requiredHeaders, maxRows })` → `{ headers, rows: [{...}], errors: [{ line, message }] }`.

Handles: quoted fields, embedded commas and newlines inside quotes, escaped `""`, CRLF and LF, a UTF-8 BOM, trailing blank lines, and header case/whitespace normalisation. Rejects: missing required headers, duplicate headers, more than `maxRows` (**5,000**) data rows, and a row whose field count differs from the header count. **No dependency** — symmetric with the parent's decision that CSV *exports* are hand-written (D-11).

### 5.5 `payroll_calculation.service.js` — engine extension

`computePayrollItem` gains three optional inputs and keeps its signature backwards-compatible (omitting them reproduces Phase-2 output byte-for-byte, which its existing tests assert):

```
computePayrollItem({ employee, structures, ledger, overtimeMinutes, settings, window,
                     basicComponentId,
                     adjustments = [],           // resolved, approved, positive amounts
                     loanInstallments = [],      // at most one per loan, pre-selected
                     carryForwardBalancePaise = 0 })
```

**Step 6b — adjustment earnings.** One component line per `adjustment_type: 'earning'`: `component_type: 'earning'`, `source: 'adjustment'`, `source_ref_id: adjustment.id`, `is_lop_applicable: false`, `full_month_amount == amount` (D-21), flags copied from the adjustment row, `display_order: 8000 + index` (after structure, before overtime's 9000).

**Steps 8b–8d — the deduction waterfall.** Order is **binding** and must be documented in the code:

| # | Class | Source | Insufficiency policy |
|---|---|---|---|
| 8a | Structure deductions | `structure` | always applied (part of the definition) |
| — | *Statutory* | `statutory` | **Phase 4** — reserved slot, nothing emitted here |
| 8b | Adjustment deductions | `adjustment` | always applied |
| 8c | **Loan EMI** | `loan` | **all-or-nothing** (EC-15) |
| 8d | **Carry-forward recovery** | `adjustment` (code `CARRY_FORWARD_RECOVERY`) | **partial allowed**, capped |

* **8c (EC-15).** For each selected installment, if `net_so_far − installment.total_amount < 0`, the installment is **skipped entirely** — no partial charge, ever. Emit warning `LOAN_EMI_SKIPPED:{loan_id}` and no component line. Because the selector re-picks the same earliest `scheduled` installment next month, the schedule slides by one month with **no row rewriting**, no renumbering, and no possibility of the two-installments-in-one-month double charge. `due_period_month` is therefore documented as *planned*, and the loan's expected closure is derived, not stored.
* **8d.** `recovery = min(carryForwardBalancePaise, max(0, net_so_far))`. Capping at the remaining net guarantees recovery can never itself create a new shortfall. Emitted as a `deduction` line with `source: 'adjustment'`, `component_code: 'CARRY_FORWARD_RECOVERY'`, `source_ref_id: null`.

**Step 9 — net, clamp and reconciliation.**

* `net_raw = Σ earnings − Σ deductions`.
* `net_raw >= 0` → unchanged from Phase 2.
* `net_raw < 0` and `negative_net_handling === 'block'` → `throw AppError(422, …, 'NEGATIVE_NET_PAY')`. The run service turns that into an `error` item (EC-12 machinery, already built) and `409 RUN_HAS_ERRORS` blocks approval.
* `net_raw < 0` and `clamp_and_carry_forward` → emit a **balancing earning line** `component_code: 'NET_PAY_SHORTFALL_CARRIED'`, `component_type: 'earning'`, `source: 'adjustment'`, `amount = −net_raw` (positive), `is_taxable: false`, `is_part_of_ctc: false`, `display_order: 9998`; set `item.carry_forward_out = −net_raw`; push warning `NEGATIVE_NET_CLAMPED`; `net = 0`.

> **Why a balancing line and not a bare clamp (D-20).** Phase 2's Assert 2 requires `Σ(earnings) − Σ(deductions) + rounding == net_pay` exactly ([payroll_calculation.service.js:351](src/modules/payroll/services/payroll_calculation.service.js#L351)). A silent clamp breaks that invariant and would throw `CTC_RECONCILIATION_FAILED` on every clamped item. The balancing line keeps the invariant true, makes the payslip self-explaining ("we owed you this, we could not pay it, it carries forward"), and mirrors the `ROUNDING_ADJUSTMENT` precedent exactly. It uses `source: 'adjustment'` rather than a new `carry_forward` enum value **deliberately**: `ALTER TYPE … ADD VALUE` cannot be used inside the same transaction that consumes it, and the reserved `component_code` gives the same queryability with none of the migration risk. Both codes — `NET_PAY_SHORTFALL_CARRIED` and `CARRY_FORWARD_RECOVERY` — are module-reserved and must be rejected by the component-catalog validator so an org cannot collide with them.

* `item.carry_forward_in = recovery` (from 8d); `item.calculation_warnings = warnings`.
* The existing sign assert is unchanged: only `source: 'rounding'` may be negative. Every Phase-3 line is positive.

**Purity is preserved.** No new import. `carryForwardBalancePaise` arrives as an integer; the service computes it.

### 5.6 `payroll_variable_pay_aggregator.service.js` — **D-17**

Read-only, batched, **cohort-scoped**, returns a `Map<user_id, …>` for one cohort. Called by `payroll_run.service.calculate` inside its existing cohort loop, so peak memory stays one cohort and query count stays O(cohorts).

```
aggregateForCohort({ orgId, cohort, periodMonth, runId })
  → Map<user_id, { adjustments: [], dueInstallments: [], carryForwardBalancePaise: number }>
```

**Three queries per cohort:**

1. `payroll_adjustments` — `org_id`, `user_id IN cohort`, `period_month = periodMonth`, `status = 'approved'`, `(applied_run_id IS NULL OR applied_run_id = runId)`.
2. `loan_installments` ⋈ `employee_loans` — `org_id`, `user_id IN cohort`, `loan.status = 'active'`, `installment.status = 'scheduled'`, `due_period_month <= periodMonth`, `(run_id IS NULL OR run_id = runId)`; reduced to one per loan by `variable_pay_selector`.
3. **Carry-forward balance** — over `payroll_run_items` ⋈ `payroll_runs`: `user_id IN cohort`, `run.status IN ('approved','paid')`, `run.period_month < periodMonth` → `SUM(carry_forward_out) − SUM(carry_forward_in)`, grouped by `user_id`, clamped at ≥ 0.

Query 3 reads only **approved/paid** runs, which is what makes recalculation idempotent: the run being calculated cannot contribute to its own input.

**Writes nothing.** As with the Phase-2 aggregator, persistence belongs to the run service.

### 5.7 `payroll_run.service.js` — calculation wiring

Inside the existing cohort loop ([payroll_run.service.js:303](src/modules/payroll/services/payroll_run.service.js#L303)):

```js
const variablePay = await variablePayAggregator.aggregateForCohort({ orgId, cohort, periodMonth: claimed.period_month, runId })
const { itemRows, componentsByUser } = this._buildCohortRows({ …, variablePay })
```

`_buildCohortRows` passes `adjustments`, `loanInstallments` and `carryForwardBalancePaise` into `computePayrollItem`, and copies `item.calculation_warnings`, `item.carry_forward_in`, `item.carry_forward_out` onto the row. `ZERO_FIGURES` gains `carry_forward_in: 0`, `carry_forward_out: 0`, and error rows set `calculation_warnings: null`.

`buildSettingsSnapshot` gains `negative_net_handling` (§2 item 6). `create()` writes `engine_version: 3` (§2 item 5).

### 6.4 Period-collision rules (**EC-31**)

|---|---|
| none, `draft`, `calculated`, `failed` | Accept. If a run exists, set `requires_recalculation = true` on it (**D-18**) — the existing `409 RUN_STALE` gate then forces HR to recalculate before approving |
| `calculating` | `409 RUN_CALCULATION_IN_PROGRESS` — retryable, and it prevents the write from racing a cohort UPSERT |
| `approved` or `paid` | `422 PERIOD_CLOSED_FOR_ADJUSTMENT`, naming the run and stating that the change must target a later month. **Never** mutate a closed run (**D-12**); true retro settlement is Phase 7 arrears |

5. `settled_externally` → no adjustment; the money is assumed received outside payroll.
6. `status = 'foreclosed'`, `foreclosed_at`, `foreclosure_reason`, `outstanding_principal = 0`, audit `loan.foreclosed`. Commit.

## 7. Transactional Behaviour

Unmanaged transactions only, `if (!t.finished) await t.rollback()` — the Phase-1/2 idiom. Every state transition writes `payroll_audit_logs` **inside its own transaction**.

### 7.1 Lock ordering (module-wide rule, **binding**)

Deadlock avoidance requires one total order. Phase 3 adopts and documents it:

```
1. payroll:run:{orgId}:{period_month}     ← ALWAYS first, whenever a live run may be touched
2. payroll:lock:{orgId}                   ← period-lock resolution (run approval only)
3. payroll:loan:{userId}  /  payroll:structure:{userId}
4. row locks (FOR UPDATE), parents before children
```

Concretely: **any Phase-3 writer that may set `requires_recalculation` on a run takes the run advisory lock before the loan/structure advisory lock.** Without this, foreclosure (loan → run) and run approval (run → loan) form a cycle. This rule must appear as a comment in every Phase-3 service that takes more than one lock.

### 7.2 Maker–checker writes (adjustment · bonus rule · loan)

All three follow the Phase-1 `employee_salary_structure.service` shape verbatim:

1. Begin transaction; load `payroll_settings`.
2. **Authority chokepoint before any existence lookup** — `getAccessibleUserIds` → `decideAuthority`. Fail `403 FORBIDDEN` identically for "not yours" and "doesn't exist" (**EC-24**).
3. `landsApproved = scope === 'global' ? !payroll_require_separate_checker : authority.canApproveFor`.
4. Resolve the target profile (`_resolveRoleProfile` three-way fallback) — safe to `404` now that scope has passed.
5. Take the §7.1 locks; run the §6.4 period-collision check.
6. **Insert `pending` first, then finalize if it should land approved** — one approval code path, exactly as Phase 1 does for structures.
7. Audit with `proposedBy` and, when finalized, `approvedBy` populated. Commit.

**Approval** (`/approve`): peek org-scoped → §7.1 locks → load `FOR UPDATE` → `status === 'pending'` else `409 PROPOSAL_NOT_PENDING` (idempotent against a double-click) → separate-checker guard (`403 SEPARATE_CHECKER_REQUIRED`, message naming both remedies) → **re-verify the original proposer's scope** (`409 PROPOSAL_SCOPE_STALE`, **EC-29**) → §6.4 period check → apply → audit → commit.

### 7.3 Loan approval (#79) — schedule generation

Inside one transaction, after the §7.2 frame:

1. Advisory `payroll:loan:{userId}`, then the loan row `FOR UPDATE`.
2. **Concurrency-sensitive policy checks happen here, not at proposal time** — `loan_max_concurrent_per_employee` is counted under the lock (`COUNT(*) WHERE user_id = ? AND status = 'active'`), because two proposals approved in parallel would each pass a check made at proposal time. Also enforce `loan_max_amount`, `loan_max_tenure_months`, `loan_max_interest_rate`.
3. `buildSchedule(...)` (§5.1) → `bulkCreate` the installments.
4. `status = 'active'`, `emi_amount`, `total_payable`, `total_interest`, `outstanding_principal = principal_amount`, `approved_by`, `actioned_at`.
5. Audit `loan.approved` with the schedule summary. Commit.

Re-issuing approve on an `active` loan is refused by the status guard, so a retry can never generate a second schedule. The UNIQUE `(loan_id, installment_number)` index is the backstop.

### 7.4 Run approval (#48) — the variable-pay commit (**D-18**)

The Phase-2 approve transaction gains one block, placed **after** period-lock resolution and **before** the run status update (§7.1 ordering):

1. Load every component line of the run's `calculated` items with `source IN ('adjustment','loan')`, joined to their items.
2. **Loan installments** — `SELECT … FOR UPDATE` every referenced installment. Each must still be `scheduled` and unstamped, else `409 LOAN_INSTALLMENT_ALREADY_DEDUCTED` naming the loan (forces a recalculation). Then set `status = 'deducted'`, `run_id`, `run_item_id`, `deducted_amount`, `deducted_at`. For each affected loan: `recovered_amount += Σ deducted`, `outstanding_principal = Σ principal of remaining scheduled`; when no `scheduled` installment remains → `status = 'closed'`, `closed_at`.
3. **Adjustments** — `SELECT … FOR UPDATE` every referenced adjustment (`source_ref_id` of `source: 'adjustment'` lines, ignoring the two engine-generated codes which carry a null ref). Each must still be `approved` with `applied_run_id IS NULL`, else `409 ADJUSTMENT_ALREADY_APPLIED`. Then stamp `applied_run_id`, `applied_run_item_id`, `applied_at`.
4. Audit `run.variable_pay_committed` with the counts, then continue with the existing status update and `run.approved` audit.

> **Why commit at approval and not at calculation.** Calculation is re-runnable by design (Phase 2 §7.2) — it UPSERTs items and replaces component lines wholesale. If it also stamped adjustments and installments as consumed, every recalculation would either double-consume or need a compensating release step that a crash could skip. Approval, by contrast, is the single, transactional, once-only transition that already carries the period lock. Consumption therefore rides on it, and `cancel` is the exact inverse. Between calculation and approval an adjustment is *referenced but not consumed*, which is precisely its real state.

### 7.5 Run cancel (#49) — the exact inverse

Inside the existing cancel transaction (`approved`, `paid_at IS NULL` only), before the status update:

1. `loan_installments WHERE run_id = ?` → `status = 'scheduled'`, `run_id = NULL`, `run_item_id = NULL`, `deducted_amount = 0`, `deducted_at = NULL`. Recompute each affected loan's `recovered_amount` / `outstanding_principal`; a loan this run had `closed` returns to `active`.
2. `payroll_adjustments WHERE applied_run_id = ?` → clear `applied_run_id`, `applied_run_item_id`, `applied_at`.
3. Audit `run.variable_pay_reversed` with the counts.

A `paid` run is never cancellable, so a paid deduction is never reversed by this path (**D-12**).

### 7.6 Bulk batches (#64) and rule application (#73)

Both are **one transaction, all-or-nothing**, with a shared `batch_id`:

* Resolve every target `user_id` **first** (from `user_id` or `employee_code`); an unresolvable or out-of-org identifier fails the **whole** batch with the offending line numbers. A partially-applied bonus upload is worse than a rejected one — half the team paid and no clean way to tell which half.
* Run the §6.4 period check **once** for the batch's `period_month`.
* Cap: 5,000 rows (`422 BULK_ROW_LIMIT_EXCEEDED`). At ~200 bytes/row that is well inside the 10 MB body limit.
* `#73` additionally takes the rule row `FOR UPDATE` and re-checks `applied_at IS NULL` inside the transaction, so a double-click produces `409 RULE_ALREADY_APPLIED`, not two batches.
* One audit row for the batch (`adjustment.bulk_created` / `bonus_rule.applied`) carrying the counts and the `batch_id`, **not** 5,000 audit rows.

### 7.7 Preview (#42) extension

The existing preview response gains a `variable_pay` block, derived from persisted component lines and item columns (never recomputed):

```
{ adjustment_earnings_total, adjustment_deductions_total, loan_recovery_total,
  carry_forward_recovered_total, carry_forward_generated_total,
  skipped_emi_count, clamped_item_count, warning_items: [{ user_id, warnings[] }] }
```

`skipped_emi_count` and `clamped_item_count` come from `calculation_warnings` — which is exactly why §4.6 persists it. HR must be able to see, before approving, that eleven people had their EMI skipped.

## 10. Exit Criteria — Phase 4 does not begin until every line is checked

**Schema & wiring**
- [ ] `00040` migrates up, down, and up again cleanly (all twelve new enum types dropped with `CASCADE`; the three `payroll_run_items` columns removed; `engine_version` default restored on `down`).
- [ ] The four new models load; **every Phase-1 and Phase-2 endpoint is regression-checked** — `/hr/settings`, `/hr/components`, `/hr/runs/:id/calculate`, `/me/salary-structure`, `/me/payslips/:runId`.
- [ ] A run calculated with **no** adjustments, loans or carry-forward produces figures **byte-identical** to the Phase-2 engine for the same inputs, with `engine_version: 3`.
- [ ] **`PUT /hr/settings` → `GET /hr/settings` round-trips every payroll setting #35–#46**, including the seven Phase-2 keys that the schema previously stripped (§11 item 15). Setting `lop_basis` through the API and recalculating changes the per-day rate.
- [ ] Creating a salary component coded `OVERTIME`, `ROUNDING_ADJUSTMENT`, `NET_PAY_SHORTFALL_CARRIED` or `CARRY_FORWARD_RECOVERY` → `422 RESERVED_COMPONENT_CODE` (§2 item 18).

**Arithmetic**
- [ ] An approved bonus, an ad-hoc deduction, an EMI and a carry-forward recovery on one item all appear as distinct component lines with correct `source` / `source_ref_id`, and `Σ earnings − Σ deductions + rounding == net_pay` **exactly** (EC-17).
- [ ] A bonus is **not** reduced for an employee with 5 LOP days (D-21).
- [ ] A reducing-balance schedule's `Σ principal` equals the principal to the paise, and `Σ total` equals `total_payable`.
- [ ] **EC-15** — an employee whose net is ₹1 short of the EMI has it **skipped entirely** (not partially charged), carries `LOAN_EMI_SKIPPED`, and the **same** installment is charged next month; the loan closes one month later with no schedule rewrite and no month in which two installments are charged.
- [ ] **EC-14** — deductions exceeding earnings clamp net to ₹0, emit `NET_PAY_SHORTFALL_CARRIED`, set `carry_forward_out`, and the next approved run recovers it via `CARRY_FORWARD_RECOVERY` capped at that month's net; the recovery never itself creates a new shortfall. With `negative_net_handling = 'block'` the same input yields an `error` item and `409 RUN_HAS_ERRORS`.
- [ ] **EC-16** — foreclosure cancels every `scheduled` installment, leaves `deducted` ones untouched, and (in `recover_via_payroll`) creates exactly one approved `recovery` adjustment for the outstanding principal.

**Authority, scope & secrecy**
- [ ] **A manager proposal for a direct report needs HR approval to reach a payslip** — a `pending` adjustment, bonus rule or loan produces **no** component line and no installment schedule (parent Phase-3 exit criterion).
- [ ] A manager proposing for a **non-report** gets `403`, byte-identical to the response for a non-existent user id (**EC-24**).
- [ ] A manager proposing a bonus rule with `eligibility_source: 'all_employees'` or `'department'` → `403 ELIGIBILITY_SOURCE_NOT_PERMITTED`.
- [ ] **EC-29** — a proposal whose subject stops reporting to the proposer before approval is blocked with `409 PROPOSAL_SCOPE_STALE`.
- [ ] `payroll_require_separate_checker` ON with a sole HR user blocks approval with a message naming both remedies (**EC-30**).
- [ ] `manager_can_view_team_compensation = false` → the manager adjustment/loan lists return no per-head figures (**EC-25**).
- [ ] An `employee` token on any `/hr` or `/manager` Phase-3 route → `403`; an `admin` / `super-admin` token → `403` everywhere (**D-14**).
- [ ] An employee sees only their own `approved` records; a `pending` proposal about them is invisible.
- [ ] HR of Org A cannot read or mutate any Org B adjustment, rule, loan or installment.

**Lifecycle, concurrency & idempotency**
- [ ] **An EMI deducts once and only once per month.** Recalculating a `calculated` run twice, then approving, charges each installment exactly once (`SELECT count(*) FROM loan_installments WHERE status='deducted'` before and after).
- [ ] Approving a run stamps every referenced adjustment and installment; **cancelling it reverses every stamp exactly**, restores `outstanding_principal` / `recovered_amount`, and reopens a loan the run had closed.
- [ ] A `rejected` or still-`pending` adjustment **never** reaches a payslip (parent Phase-3 exit criterion).
- [ ] **EC-31** — approving an adjustment whose `period_month` belongs to an `approved` or `paid` run → `422 PERIOD_CLOSED_FOR_ADJUSTMENT`, the closed run is unchanged; approving one for a `calculated` run sets `requires_recalculation`, and approving that run then fails `409 RUN_STALE` until it is recalculated.
- [ ] Approving an adjustment while its period's run is `calculating` → `409 RUN_CALCULATION_IN_PROGRESS`, and nothing is written.
- [ ] Two concurrent `POST /bonus-rules/:id/apply` → one batch, one `409 RULE_ALREADY_APPLIED`.
- [ ] Two concurrent `POST /loans/:id/approve` → one schedule.
- [ ] `loan_max_concurrent_per_employee = 1` with two loans approved concurrently → one `active`, one rejected by the under-lock count.
- [ ] A bulk upload with one bad row on line 400 persists **nothing** and names line 400.
- [ ] A 5,001-row upload → `422 BULK_ROW_LIMIT_EXCEEDED`.
- [ ] Every create, approve, reject, cancel, apply, foreclose, commit and reversal appears in `payroll_audit_logs` with actor, `proposed_by`/`approved_by` where applicable, and reason. A 5,000-row batch writes **one** audit row, not 5,000.

**Performance & tests**
- [ ] A 500-employee run with variable pay issues **3 extra queries per cohort** over the Phase-2 baseline (verified by query log) — the total stays O(cohorts), not O(employees).
- [ ] `npm test` passes: the Phase-1 and Phase-2 suites **and** the four new Phase-3 suites plus the two extended ones.

## 11. Risks & Decisions Needed

| # | Item | Recommendation | Needed by |
|---|---|---|---|
| 1 | **When is an adjustment/installment "consumed"?** Doing it at calculation makes recalculation double-consume or need a fragile release step; doing it never makes double-payment possible across runs. | **D-18** — consume at **run approval**, reverse at **cancel**, both inside the existing transactions. Calculation only *references*. This is the single most important correctness decision in the phase. | Before §7.4 |
| 2 | **No upload infrastructure exists** (§2 item 14) yet the parent requires bulk CSV. Adding `multer` means a dependency, a temp-file lifecycle, and an upload-size attack surface for one feature. | **D-19** — accept the CSV as a **string field in the JSON body** (`csv_content`) *or* a `rows[]` array, parsed by a hand-written pure `csv_parser.utils.js`. Zero dependencies, symmetric with D-11's hand-written exports, bounded by the existing 10 MB body limit and a 5,000-row cap. Revisit only if Phase 5 needs real file attachments, which it does — and that is Phase 5's decision to make. | Before §5.4 |
| 3 | **A clamped negative net breaks Phase 2's reconciliation assert** and would throw `CTC_RECONCILIATION_FAILED` on every clamped item. | **D-20** — emit an explicit `NET_PAY_SHORTFALL_CARRIED` balancing earning line, mirroring `ROUNDING_ADJUSTMENT`. Reuse `source: 'adjustment'` with reserved component codes rather than adding a `carry_forward` enum value: `ALTER TYPE … ADD VALUE` cannot be consumed in the transaction that adds it, and the reserved codes give identical queryability. **The component-catalog validator must reject all four engine codes** — `OVERTIME` and `ROUNDING_ADJUSTMENT` are already unreserved today (§2 item 18), so an org that created a component coded `OVERTIME` would already produce two indistinguishable lines on one payslip. | Before §5.5 |
| 4 | **Is a bonus reduced by LOP or prorated for a joiner?** Silently scaling an authorised rupee figure is a dispute waiting to happen. | **D-21** — no. Adjustments are never LOP-applicable and never prorated; the approved amount is the paid amount. An org wanting proration approves a pro-rated figure. Percentage bonus bases resolve against the **salary structure**, not the run's LOP-reduced gross, so a preview cannot diverge from the payout. | Before §5.2 |
| 5 | **Two installments due in one month** after a skip (EC-15) would double-charge, and rewriting `due_period_month` on a skip would mutate a schedule an employee has already seen. | Selector takes **the earliest scheduled installment with `due_period_month <= period_month`, one per loan, always** (§5.3). The schedule slides by one month with zero row mutation. `due_period_month` is documented as *planned*; expected closure is derived. | Before §5.3 |
| 6 | **Loan status enum diverges from the D-13 quartet** (no `approved` value). | Accept and document (**D-21**, §4.3): for a loan, approving *is* activating, so a persisted `approved` would be a dead state — and a dead state in a money table eventually gets read. `approved_by` + `actioned_at` still record the checker; `pending`/`rejected`/`cancelled` keep quartet semantics. | Before §4.3 |
| 7 | **Foreclosure ↔ run approval deadlock.** Foreclosure walks loan → run (to set `requires_recalculation`); run approval walks run → loan. | §7.1's total lock order: **run advisory before loan advisory, always.** Must be a comment in every multi-lock Phase-3 service, not just this document. | Before §7.1 |
| 8 | **Late-approved variable pay silently missing from a calculated run.** | Reuse the existing `requires_recalculation` + `409 RUN_STALE` gate (§6.4) rather than inventing a staleness concept. Zero new machinery, and HR already knows the error. | Before §6.4 |
| 9 | **`ENGINE_OWNED_COLUMNS` is an easy miss.** A new engine column left out of the allow-list keeps its first-calculation value forever, silently. | Add all three §4.6 columns in the same commit as the migration, and add an exit-criterion check that recalculating changes them. | Before §5.7 |
| 10 | **Interest on foreclosure** — recover principal only, or principal plus accrued interest to date? | Principal only, interest on cancelled installments **forgiven**. Conventional, employee-favourable, and simple to explain on the payslip. State it in the foreclosure response so it is never a surprise. | Before §6.5 |
| 11 | **Bulk batches are all-or-nothing**, so a 5,000-row upload with one typo is fully rejected. | Accept — and mitigate with the mandatory `#63 bulk/preview` step, which reports every bad row at once. Partial application of a bonus batch is a far worse failure: half a team paid, no clean rollback, and no way to tell which half without a diff. | Before §7.6 |
| 12 | **Phase-3 bonuses are paid with no TDS** and will look wrong to anyone who knows Indian payroll. | Intentional and machine-flagged: `statutory_status: 'not_applied'`, `engine_version: 3`. Phase 4 owns withholding, including on variable pay. Communicate before any demo. | Communication |
| 13 | **`performance_rating` eligibility has no data source** (D-9). | Validate the value, evaluate to all-skipped with `ELIGIBILITY_SOURCE_UNAVAILABLE`, `422` on apply. No hard dependency, no stub table, and the wiring point is one function when the Performance module lands. | Before §5.2 |
| 14 | **The parent's §0 status line is stale** — it claims Phases 2–7 are not started while Phase 2 is fully implemented. Anyone planning Phase 4 from it will repeat this phase's reconciliation work. | Correct it as part of §9 item 5, and treat the parent's status line as a required edit at the **end of every phase**, not an optional one. | Before Phase 4 |
| 15 | **Pre-existing defect: registry settings #41–#44 cannot be set through the API** (§2 item 17). `updateSettingsSchema` never gained the Phase-2 keys, so `lop_basis`, `net_pay_rounding`, `in_progress_treatment` and the four overtime knobs are only changeable by direct DB edit — and when the request carries any *valid* key alongside, the API returns **`200 OK` while silently discarding them**. Phase 2's own exit criterion "changing `lop_basis` and recalculating changes the per-day rate" cannot have been exercised through the product. **Severity: HIGH** — a silent no-op on a money-affecting setting is worse than a rejection, because an org can believe it has switched LOP basis and run a month's payroll on the old one. | **Fix it in this phase**, in the same edit that adds the §4.5 keys. ## 12. Build Order & Dependencies

Each step leaves the system **deployable and green**. Steps 1–4 change no runtime behaviour at all; the engine does not see variable pay until step 6, and no HTTP surface exists until step 8. This ordering exists so that the two genuinely dangerous changes — touching the engine and touching run approval — land against tests that already pass.

| # | Step | Depends on | Done when |
|---|---|---|---|
| 1 | Migration `00040` (§4) + the four models + the three `payroll_run_items` columns + `engine_version` default | — | `db:migrate` → `undo` → `migrate` is clean; Phase-1/2 endpoints regression-checked |

| 5 | **Engine extension** — Steps 6b, 8b–8d, 9-clamp (§5.5) | 3 | Extended `payroll_calculation.test.js` passes **and** the Phase-2 assertions still pass unchanged with the new inputs omitted |
