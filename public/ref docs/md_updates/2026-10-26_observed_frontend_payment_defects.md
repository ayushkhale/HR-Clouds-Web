## 1. Defect BUG-PAY-001: Dismissed Payment Results in Duplicate Organization Creation

### Severity: High (Business Logic & Data Hygiene)
### Location: `src/auth/pages/RegisterOrgPage.jsx` (Razorpay modal `ondismiss` handler)

### Description
When a user begins payment for a paid plan, Razorpay's checkout modal is rendered with an `order_id` generated by `organizationAPI.initiateRegistration`. 
If the user closes or dismisses the Razorpay modal without completing the payment:
1. The modal `ondismiss` callback executes:
   ```javascript
   modal: {
     ondismiss: () => {
       setLoading(false);
       setError("Payment was cancelled. You can retry anytime — your organization has been saved.");
     }
   }
   ```
2. The user is presented with the message: *"Payment was cancelled. You can retry anytime — your organization has been saved."*
3. However, if the user clicks "Proceed to Payment" again, the form invokes `handleSubmit` and calls `organizationAPI.initiateRegistration` again.
4. Per the backend registration contract (`1_org_registration_api.md` §1), each invocation of `initiateRegistration` creates a **brand new `organizations` row** in the database with a new `org_id` and generates a new payment order.
5. The previously stored `PENDING_ORG_KEY` (`hrclouds_pending_org_id` in `sessionStorage`) is overwritten.

### Impact
- Orphaned, pending organization rows accumulate in PostgreSQL.
- The UI reassurance (*"your organization has been saved"*) contradicts the action taken (creating an entirely new organization).
- If the customer was attempting to preserve an organization name or alias that is unique, a second submission might fail with conflict errors.

### Recommended Remediation
1. **Frontend Flow:** On `ondismiss`, check if `sessionStorage.getItem(PENDING_ORG_KEY)` is present.
2. If the user clicks "Retry Payment" without changing organization details, re-open Razorpay against the existing pending order instead of initiating a brand new organization registration.
3. Alternatively, have backend support an idempotent `initiateRegistration` that accepts `existing_org_id` if a transaction is still in `pending_payment` status.

## 2. Defect BUG-PAY-002: Lack of Automatic Transient Retry on Verification Failure

### Severity: Medium (Customer Experience & Conversion)
### Location: `src/auth/pages/RegisterOrgPage.jsx` (Razorpay `handler` payment verification)

### Description
In `RegisterOrgPage.jsx`, when Razorpay completes a transaction and returns `paymentRes`, the frontend makes an HTTP call to `organizationAPI.verifyPayment`:
```javascript
const verifyRes = await organizationAPI.verifyPayment({
  razorpay_payment_id: paymentRes.razorpay_payment_id,
  razorpay_order_id: paymentRes.razorpay_order_id,
  razorpay_signature: paymentRes.razorpay_signature,
  org_id: orgId,
});
```
If a transient network glitch or momentary gateway timeout occurs (e.g. 502/504 or Network Error), the catch block immediately displays:
> *"Payment was received but organization setup is pending. Don't pay again — check your email or contact support."*

### Impact
- Per backend specification `1_org_registration_api.md` §2 ("Important Side Effects"):
  > *"The endpoint is idempotent and the frontend can safely retry this API."*
- Bailing out immediately on the first network failure frightens paying customers and causes unnecessary inbound support tickets, when a single automatic exponential backoff retry (e.g. 1 retry after 1.5 seconds) would recover >95% of transient dropped packets.

### Recommended Remediation
Implement a single bounded retry (1 attempt after a 1.5s delay) inside the verification handler for 5xx/network errors before displaying the failure message.

## 3. Defect BUG-PAY-003: Sub-optimal Size Filter Calculation against Billing Cycles

### Severity: Minor (UI Guidance Consistency)
### Location: `src/auth/pages/RegisterOrgPage.jsx` (`sizesForPlan` vs `selectedLimits`)

### Description
In `RegisterOrgPage.jsx`, the function `sizesForPlan(plan)` originally evaluated seat limits from `plan.limits.employees` (the default monthly limit), whereas the help guidance beneath the dropdown reads `selectedLimits.employees` (the variant limit). While current plans have identical employee caps between monthly and annual cycles, any future plan tier with differentiated yearly seat capacity would cause the dropdown options to diverge from the hint text.

### Remediated Note
In the updated `RegisterOrgPage.jsx`, we aligned `sizesForPlan(plan, billing)` to use `limitsFor(plan, billing).employees`, eliminating the discrepancy.
